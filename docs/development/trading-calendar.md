# NYSE Session-Date Validation

## Requirement And Design

Phase 4 must not compare returns over incompatible intervals. Exact equality of
two input date axes still permits a shared missing trading session. The optional
`--calendar XNYS` diagnostic gate therefore compares the complete input axis
with dates generated by `exchange-calendars==4.13.2`, pinned with transitive
dependencies and hashes in the root `uv.lock`.

This starts the calendar portion of Phase 5 without declaring Phase 4 complete.
No new service, database table, provider adapter or generic calendar framework is
introduced. Python owns date resolution; Rust orchestration and TypeScript
provider code are unchanged. The library is loaded only when the gate is used.

The adapter accepts inclusive dates within 2005-01-01 through 2026-12-31. These
explicit initial research bounds limit schedule generation and avoid the
library's wall-clock-relative defaults. Extending the supported window requires
a reviewed change and renewed calendar fixtures, not silently changing existing
reports. The entire approved historical range through 2026-08-31 is exercised.

Only XNYS is exposed. It is not an assertion that NYSE and every other US venue
are interchangeable. Broader security-specific calendar selection belongs with
the Security Master and execution policy. No holiday rules are hand-written in
the application; tests independently check the exchange's published dates.

## Evidence Boundaries

`CalendarEvidence` contains the calendar name, installed package version and
`session_dates_sha256`. This digest is SHA-256 of the ordered ISO dates, each
terminated by ASCII LF. It identifies the generated date list, not a complete
intraday calendar or the production trading-calendar provenance component.

The gate rejects missing or extra dates anywhere inside the reported endpoints,
duplicate/unsorted observations, weekend/holiday rows and unsupported bounds.
It does not detect a truncated intended sample outside those endpoints.
Early-close days remain sessions; no claim about correct NAV timestamps or
execution hours follows. Future rules can change, including exceptional
closures, so this is not PIT knowledge or a future market-opening guarantee.

NAV reports remain `unverified_local_input` even after calendar validation.
Authoritative data snapshots, immutable full-calendar manifests, original-run
resolution, permission checks and six-component execution provenance are still
required before this can support an admitted factor or official backtest.

## Verification And Sources

Tests cover the published 2026 NYSE holiday dates, the two published early-close
dates, shared gaps, one-day queries, strict ordering, bounded ranges/scans,
deterministic date hashes, the full 2005-to-August-2026 generation path and actual
CLI success/failure. They run offline against the installed library. Calendar
generation is not a market-data download or a holdout evaluation.

- [NYSE holidays and trading hours](https://www.nyse.com/trade/hours-calendars),
  consulted 2026-09-10, supplies the independent 2026 date fixtures.
- [exchange_calendars 4.13.2](https://pypi.org/project/exchange-calendars/4.13.2/)
  documents XNYS queries, Python 3.14 support and the Apache-2.0 license.

The upstream distribution has no PEP 561 typing marker. Only that import uses
an `import-untyped` annotation; this adapter converts returned labels into
validated standard-library dates and tests the third-party library boundary.
No application type checking is disabled globally.

## Rollback

Revert this calendar-gate commit and restore its previous lockfile/research
package. The original interval-only NAV diagnostic and `doctor` remain usable.
No schema migration or data removal is necessary. Keep previously emitted
reports with their recorded library version/date digest; never relabel their
checks under a new library version. Full dependency SBOM/license review remains
a release gate.
